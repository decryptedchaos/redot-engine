## 2. Godot 4.5 module facts

Sources: [Custom modules in C++](https://docs.godotengine.org/en/4.5/engine_details/architecture/custom_modules_in_cpp.html),
[build system](https://docs.godotengine.org/en/4.5/engine_details/development/compiling/introduction_to_the_buildsystem.html),
[`register_module_types.h`](https://github.com/godotengine/godot/blob/4.5/modules/register_module_types.h).

- Required files live at the module root. The initialization function name must match the folder
  name: `initialize_debug_menu_module` / `uninitialize_debug_menu_module`.
- Levels: `MODULE_INITIALIZATION_LEVEL_CORE`, `SERVERS`, `SCENE`, `EDITOR`.
- Classes: `ClassDB::register_class<T>()` or `GDREGISTER_CLASS(T)`.
- Project settings: `GLOBAL_DEF` / `GLOBAL_GET`; module defaults are legitimate.
- Engine singletons: `Engine::get_singleton()->add_singleton(Engine::Singleton("Name", obj))` and
  `remove_singleton("Name")`. `Engine::Singleton` has name, pointer and optional class-name hint.
- Editor-only code: `TOOLS_ENABLED` and `if env.editor_build:` in `SCsub`. This module does not need
  editor-only code.
- Doc classes: `config.py` exposes `get_doc_path()` and `get_doc_classes()`; `--doctool <path>`
  regenerates XML into the module folder.
- Enable/disable: `module_debug_menu_enabled=yes|no`; `custom_modules=` is available for out-of-tree
  modules but a built-in module is the right choice here.

## 3. Bootstrap research

Sources: [godot-cpp #1180](https://github.com/godotengine/godot-cpp/issues/1180),
[godot-cpp #1597](https://github.com/godotengine/godot-cpp/issues/1597),
[godot-proposals #10928](https://github.com/godotengine/godot-proposals/issues/10928),
[`SceneTree` docs](https://docs.godotengine.org/en/4.5/classes/class_scenetree.html),
[`MainLoop` docs](https://docs.godotengine.org/en/4.5/classes/class_mainloop.html).

- `SceneTree::get_singleton()` is an internal C++ accessor in the engine headers; it is not a
  registered scripting singleton and carries no compatibility guarantee.
- `call_deferred` during scene-level module/GDExtension initialization is a known technique for
  reaching singletons that are created later; there is no formal promise about the exact frame.
- Proposal #10928 documents an attempt to add a node to the root from a scene-level initializer
  that crashed because it ran too early. This is why the module defers and validates.
- This checkout's startup order is favorable: module init happens in `Main::setup2`, `Main::start`
  does not flush the queue, and the first flush occurs inside the live `SceneTree`. The singleton is
  set in the `SceneTree` constructor. The implementation still retries twice and supports explicit
  `install()` as a fallback.
- Custom `MainLoop` types are legal (`application/run/main_loop_type`); the module casts and skips
  when the main loop is not a `SceneTree`.
- Threading: the active scene tree is not thread-safe; `call_deferred` is the documented way to hand
  work back to the main thread ([Thread-safe APIs](https://docs.godotengine.org/en/4.5/tutorials/performance/thread_safe_apis.html)).
- Shutdown: the main loop (and therefore the overlay node) is deleted before module uninitialization.
  The module must not hold raw node/tree pointers across that boundary.

Verified in this checkout:

- `servers/rendering/rendering_server.h:1201-1203` — `viewport_set_measure_render_time`,
  `viewport_get_measured_render_time_cpu`, `viewport_get_measured_render_time_gpu`.
- `servers/rendering/rendering_server.h:1911` — `get_frame_setup_time_cpu`.
- `servers/rendering/renderer_viewport.cpp:1652` — GPU time is
  `(time_gpu_end - time_gpu_begin) / 1000 / 1000` ms; unsupported backends leave both at zero.
- `Viewport::is_using_taa()` (`scene/main/viewport.h:591`), `get_scaling_3d_mode/scale`,
  `get_msaa_3d/2d`, `get_screen_space_aa`.
- `Environment` accessors are `is_ssr_enabled()`, `get_ssr_max_steps()`, `is_ssao_enabled()`,
  `is_ssil_enabled()`, `is_sdfgi_enabled()`, `get_sdfgi_cascades()`, `is_glow_enabled()`,
  `is_volumetric_fog_enabled()`.
- `OS::get_video_adapter_driver_info()` returns `Vector<String>` in this checkout.
- `OS::is_in_low_processor_usage_mode()` and `get_low_processor_usage_mode_sleep_usec()`.
- `DisplayServer::window_get_vsync_mode()` and the `VSYNC_ENABLED/ADAPTIVE/MAILBOX` enum.

Caveats that shaped the design:

- Render-time APIs measure rendering work, not total frame wall time; CPU and GPU values overlap and
  must not be added together and called "frame time".
- GPU timestamps can be unavailable; values of 0 are not proof that rendering took no time. The
  add-on displays 0.00 in that case; the native module keeps that default and offers an opt-in
  "n/a" display.
- The first `OS.get_video_adapter_driver_info()` call can block for seconds on some NVIDIA systems.
  It is cached and run on a worker thread.
- `Performance.TIME_FPS` updates once per second; the overlay computes its own FPS from frame
  deltas.
- Percentiles/1% lows are only meaningful with a large enough sample; the module documents that and
  exposes `debug_menu/history_frames`.

## 5. Reference add-on analysis

Local files: `debug_menu/debug_menu.gd`, `debug_menu/debug_menu.tscn`, `debug_menu/plugin.gd`,
`debug_menu/plugin.cfg` (version 1.2.0, author Calinou, MIT).

Upstream: [godot-extended-libraries/godot-debug-menu](https://github.com/godot-extended-libraries/godot-debug-menu)
(`addons/debug_menu/debug_menu.gd` on `master`).

Findings:

- The local script matches upstream master in the measured behavior, including the graph scale
  clamp. This is an upstream bug, not a local modification.
- The plugin adds an autoload (`add_autoload_singleton("DebugMenu", "res://addons/debug_menu/debug_menu.tscn")`).
  The untracked folder sits at the repository root, not under `addons/`, so it cannot be installed
  as-is; baseline testing must copy it to `addons/debug_menu/` in a scratch project.
- The script disables thread-safety checks (`Thread.set_thread_safety_checks_enabled(false)`) and
  updates Labels and RenderingServer calls from a worker thread. The native port avoids this.
- The script's hidden state freezes sampling; the native port samples in the background so
  `get_stats()`, monitors and recording stay meaningful, without changing visuals.
- The scene root is a `CanvasLayer` with `layer = 128`; the autoload renames it to `DebugMenu`.
- Node tree: `DebugMenu` Control (400×400 top-right) → `VBoxContainer` → FPS/FrameTime/FrameNumber,
  `FrameTimeHistory` grid, four graph rows (`Title` + `Graph` Panel), `Information`, `Settings`.
- Styling is entirely theme overrides: font sizes 18/12, outlines 5/3, separation 0, panel background
  `Color(0, 0, 0, 0.25098)`, information/settings modulate alpha `0.752941`.
- Gradient stops: `(0.0, #EF4444)`, `(0.3333, #FACC15)`, `(0.6667, #80E25F)`, `(1.0, #38BDF8)`.
- Graph math bug: `_total_graph_draw`, `_cpu_graph_draw` and `_gpu_graph_draw` clamp frame times in
  milliseconds to `GRAPH_MIN_FPS`/`GRAPH_MAX_FPS` (10–160) and then remap as if they were FPS.
  At 60 FPS (16.67 ms) the y coordinate is about 23.9 of 25, so those three graphs are effectively
  flat near the bottom. The native module maps ms → FPS first (D-1) and offers a legacy setting.
- FPS cap bug: `low_processor_max_fps` is applied even when low-processor mode is off, so a cap
  above `1000000/sleep_usec` is displayed incorrectly. Native fixes it (D-3).
- `frame_history_gpu_max` and other GPU colors use `1000.0 / frametime` for color, consistent with
  the D-1 fix.

## 6. Visual parity approach

Sources: [Label](https://docs.godotengine.org/en/4.5/classes/class_label.html),
[Control](https://docs.godotengine.org/en/4.5/classes/class_control.html),
[Font](https://docs.godotengine.org/en/4.5/classes/class_font.html),
[ThemeDB](https://docs.godotengine.org/en/4.5/classes/class_themedb.html),
[CanvasItem](https://docs.godotengine.org/en/4.5/classes/class_canvasitem.html),
[Label source](https://github.com/godotengine/godot/blob/4.5/scene/gui/label.cpp),
[theme item bindings](https://github.com/godotengine/godot/blob/4.5/scene/gui/button.cpp).

- `Label` performs shaping, direction/language handling, line breaking, alignment, stylebox margins,
  line/paragraph spacing, outline/shadow order and oversampling. Reproducing that by hand is a
  reimplementation of Label, not a simple draw call.
- Real `Label` nodes inherit the project theme exactly like the add-on, so custom project themes
  produce identical results.
- Theme override keys verified in this checkout by `BIND_THEME_ITEM`:
  `font_outline_color`, `outline_size`, `line_spacing`, `font_size`, `separation`,
  `h_separation`, `v_separation`, `panel`.
- Graph backgrounds use a plain filled rect, equivalent to the add-on's default `StyleBoxFlat`
  (no border, no corner radius, no shadow).
- Unicode is built with `String::chr` because MSVC's execution charset is not guaranteed to be UTF-8.

## 7. Rejected alternatives

| Alternative | Why rejected |
| --- | --- |
| Engine hook in `main/main.cpp` | Explicitly not wanted: the module must be self-contained. Kept as an escalation if the deferred bootstrap proves unreliable. |
| Native EditorPlugin that writes a `.tscn` and registers an autoload | Writes into the user's project, requires editor activation and is not self-contained at runtime. |
| Module injects a `ProjectSettings` autoload with a virtual resource loader | Relies on undocumented loader behavior, pollutes the autoload list, fragile for exports. |
| Native node class only, user adds it manually | Not drop-in; loses the add-on's zero-setup behavior. |
| Node-free RenderingServer canvas + `Font::draw_string` HUD | Can match a constrained single-line label, but must reimplement Label layout, clipping, theme lookup, oversampling, alignment, input/accessibility; high risk of visual drift. Documented as Plan B. |
| GDExtension instead of a module | User asked for a native Redot module; the engine already builds modules, and this avoids shipping a separate binary. |

## 8. Testing research

Sources: [unit testing docs](https://docs.godotengine.org/en/4.5/engine_details/architecture/unit_testing.html),
[`tests/test_main.cpp`](https://github.com/godotengine/godot/blob/4.5/tests/test_main.cpp),
[`test_split_container.h`](https://github.com/godotengine/godot/blob/4.5/tests/scene/test_split_container.h),
[`test_control.h`](https://github.com/godotengine/godot/blob/4.5/tests/scene/test_control.h),
[Godot GUI testing proposal](https://github.com/godotengine/godot-proposals/issues/1760).

- `TEST_CASE("[SceneTree][...]")` gives the test a real `SceneTree`, mock display server,
  `MessageQueue` and `ThemeDB`; controls can be added to the root, laid out, and asserted.
- `MessageQueue::get_singleton()->flush()` is required before checking container layout.
- Theme overrides can be checked with `get_theme_*`/`has_theme_*_override`.
- Headless runs disable real rendering; visual regression must be a separate, rendering-enabled
  capture-and-compare workflow with tolerances (AA/driver differences make exact equality fragile).
- The module's tests therefore assert geometry, theme values, text and state, not pixels; visual A/B
  is a manual/MCP step.

## 9. Open items

- The graph-scale deviation (D-1) is the only intentional visual difference; it can be reverted via
  a setting or switched to default-legacy on request.
- If the deferred bootstrap is rejected by a future engine change, the fallback is a small
  `Main::start` hook (needs approval) or a native EditorPlugin-managed autoload.
- Release behavior is a project setting defaulting off in release templates; teams can opt in per
  project.
